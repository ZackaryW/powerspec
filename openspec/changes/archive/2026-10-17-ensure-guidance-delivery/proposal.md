# Proposal

## Why

The configured zmem workflow can be absent from persistent OpenSpec guidance and suppressed by service availability, while doctor reports only executable readiness. Users cannot distinguish selected policy, installed hooks, generated instructions, host receipt, and actual adherence.

## What Changes

- Publish the zmem task trigger as persistent context and unconditional startup/compaction guidance from one shared body file.
- Add contained `body_file` support to context attachments and traits, preserving their separate evaluation timing and skill-reference classification.
- Extend `doctor --agent codex|claude` with read-only checks for selection, published context, expected native registrations, observable disabled settings, actual resolver output, and explicitly unverified host receipt/adherence.
- Keep the rule visible when zmem or source metadata is unavailable, with explicit fallback guidance.
- Test missing services, disabled hooks, exclusions, incomplete sources, and both delivery events without changing user hook enablement.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `profile-skill-bundles`: Shared contained guidance files and persistent/runtime zmem selection.
- `trait-hook-delivery`: Unconditional standing zmem trigger and explicit fallback.
- `cli-product-surface`: Agent-specific delivery diagnostics with honest evidence limits.

## Impact

Catalog validation/loading, bundled zmem resources, doctor CLI and feature-owned diagnostics, tests, and user documentation. No per-prompt hooks, automatic trust/enablement changes, host-specific hash emulation, service installation, or bootstrap implementation. Active OpenSpec artifacts stay outside local checkpoint commits; no pushes.
